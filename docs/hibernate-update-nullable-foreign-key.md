# `UPDATE ... sales_order_id = NULL` がエラーにならない理由

## 結論

次のSQLは、`sales_order_id` がNULLを許可する列であればエラーになりません。

```sql
update sales_order_lines
set product_code = ?, sales_order_id = ?
where id = ?
```

このデバッグラボのバグ状態では、`PEN` 明細の `sales_order_id` へ `null` がバインドされます。外部キーは「存在する親を参照している値」を検査しますが、NULLを禁止していない限り、NULLそのものは外部キー違反ではありません。そのため、子レコードは削除されず、親との関連だけが外れます。

## このプロジェクトのテーブル定義

SQLモデルでは、子テーブルを次のように定義しています。

```sql
CREATE TABLE sales_order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_code VARCHAR(255),
    sales_order_id BIGINT,
    CONSTRAINT fk_sales_order_lines_sales_order
        FOREIGN KEY (sales_order_id) REFERENCES sales_orders (id)
);
```

`sales_order_id BIGINT` には `NOT NULL` がないため、`NULL` を格納できます。対応するJavaモデルでも、子側の `salesOrder` はnullableであり、`removeLine()` は関連を外すときに `line.assignTo(null)` を呼びます。

## バグ状態で起きること

`orphanRemoval = false` の状態で `PEN` を親コレクションから外し、子側の親参照をnullにすると、Hibernateは子行の外部キーをNULLへ更新します。

実際のSQLとバインド値は、[バグ状態のテスト実行ログ](01-bug-reproduction.log)で確認できます。

```sql
update sales_order_lines
set product_code = ?, sales_order_id = ?
where id = ?
```

バインド値は次の意味です。

| プレースホルダー | 値 | 意味 |
| --- | --- | --- |
| 1番目 | `PEN` | 現在の商品コード |
| 2番目 | `NULL` | 親注文との関連を外す |
| 3番目 | 対象明細のID | 更新する子行 |

`product_code` は変更していません。それでもSQLに含まれるのは、この構成のHibernateが更新可能な列を含むUPDATE文を生成するためです。商品コードまで変更されたことを示すログではありません。

更新後の状態は次のとおりです。

| 観測項目 | 値 |
| --- | --- |
| 注文 `SO-001` に属する明細数 | 1 |
| `sales_order_lines` の総件数 | 2 |
| `PEN` の `sales_order_id` | `NULL` |

つまり、SQLが成功することは「明細を削除できた」ことの証拠ではありません。親子の関連が外れたことと、子レコードが物理削除されたことは別に確認します。

## `NOT NULL` を付けた場合

次のように外部キー列をNULL禁止にすると、同じUPDATEは失敗します。

```sql
sales_order_id BIGINT NOT NULL,
CONSTRAINT fk_sales_order_lines_sales_order
    FOREIGN KEY (sales_order_id) REFERENCES sales_orders (id)
```

この場合、`sales_order_id = NULL` はNOT NULL制約違反になり、トランザクションはロールバックされます。これは削除漏れを直す方法ではなく、関連を外すという操作自体を許可しない設計です。

## 修正後のSQL

親に完全に従属する明細を、関連から外した時点で物理削除する要件なら、`@OneToMany(orphanRemoval = true)` を指定します。修正後、このラボでは次のSQLが発行されます。

```sql
delete from sales_order_lines where id = ?
```

このとき、注文に属する明細数と子テーブルの総件数は、どちらも1になります。

## 確認手順

1. [orphan-removal-model.sql](orphan-removal-model.sql) の `orphanRemoval = false` 相当のブロックを実行し、関連に属する明細数が1、総件数が2になることを確認します。
2. 同ファイルの `orphanRemoval = true` 相当のブロックを実行し、両方の件数が1になることを確認します。
3. アプリケーションでは `mvn test` を実行し、親コレクションと子テーブル全体の両方を検証します。
